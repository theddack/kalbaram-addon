## 0. 먼저: 하지 않은 것 · 확인 못 한 것

- **실제 게임 확인 0건.** 아래 숫자는 전부 계산·테스트끼리의 비교다.
- **추천 계산식·가중치는 건드리지 않았다.** 이번 Phase 는 캐시 열쇠와 갱신 조건만 손댔다. 기준선 263 장면 결과는 Phase 2 와 **완전히 같다**(B3 수정으로 바뀐 장면 0).
- **D2(맨몸 기준값 과대평가) 재측정은 하지 않았다.** 개발 계획의 Phase 3 에는 들어 있었지만, 이번 지시가 "캐시 및 관련 갱신 조건만" 이라서 뺐다. 다음 Phase 로 미룬다.
- main 병합·태그·릴리스 안 함. PR 도 안 열었다.
- 회복량이 **한 게임 안에서 몇 번이나 바뀌는지**는 실제 기록으로 세어 본 적이 없다. 바뀔 때마다 빌드 3종을 다시 계산한다(아래 3장).

## 1. 고친 곳 — 캐시 열쇠 6곳

상대 회복량(`Stats.TARGET.HEAL`)은 치유 감소 아이템 값의 근거인데 열쇠에 빠져 있었다. 회복량만 바뀌면 옛 결과가 그대로 나왔다.

| # | 자리 | 파일 | 무엇을 기억하나 |
|---|---|---|---|
| 1 | `memoKey` | `web/scoring.js` | 증강 기여(`gains`) · 추천 빌드(`build`) |
| 2 | `counterCache` | `web/app.js` | 🛡️ 적 대응 아이템 |
| 3 | `tierCache` | `web/app.js` | 증강 연계 티어 |
| 4 | `verdictCache` | `web/app.js` | 산 아이템 평가 |
| 5 | `buyNowMemo` | `web/app.js` | ⚡ 지금 골드로 살 것 |
| 6 | `liveLast` | `web/app.js` | 게임 연동 '다시 그릴지' 판단 |

6번은 특히 **갱신 조건**이다: 회복량이 열쇠에 없으면 변화가 '작은 변화'로 분류돼 다음 구매만 다시 그리고 빌드·티어는 건너뛰었다.

확인용으로 `Scoring.memoStats()` 를 더했다 — 적중(hit)·빗나감(miss)·크기·적중률만 돌려준다. 계산에는 영향이 없다.

### 2.3 성능

`node tools/perf_check.js` (대표 챔피언 16명 × 3번). 수정 전은 `HEAD~1` 의 `web/` 으로 같은 도구를 돌렸다.

| 장면 | 차가움 평균 (전 → 후) | 따뜻함 평균 (전 → 후) |
|---|---|---|
| 다음 구매 (증강 없음) | 4.86 → 4.67 ms | 4.54 → 4.26 ms |
| 다음 구매 (증강 2개 + 연계) | 15.21 → 14.87 ms | 15.57 → 15.11 ms |
| 증강 선택 등급 | 84.79 → 85.07 ms | 0.90 → 0.84 ms |
| 빌드 3종 | 470.86 → 472.03 ms | 0.06 → 0.06 ms |

차이는 전부 측정 흔들림 수준이다. **'따뜻함'(같은 입력 재호출)이 그대로 0.06 ms** 라는 게 핵심 — 열쇠를 늘렸지만 캐시가 헛돌지 않는다.

적중률 (갈리오, 게임 연동처럼 같은 상태로 3초마다 빌드 3종을 다시 그릴 때):

| 회차 | 적중률 |
|---|---|
| 같은 상태로 9번 | **100%** (hit 27 / miss 0) |
| 적이 흡혈 아이템을 사서 회복량 0 → 370 인 회차 | 0% (miss 3 — 빌드 3종을 다시 계산) |
| 그 뒤 같은 상태로 9번 | **100%** (hit 27 / miss 0) |

즉 회복량이 바뀐 **그 회차만** 다시 계산한다(빌드 3종 ≈ 0.5초, 화면은 `warmThenRender` 로 쪼개 계산). 과잉 무효화는 없다.

## 3. 테스트

### 3.1 새 테스트 6개 — 전부 수정 전에는 실패하는 것을 확인했다

`tests/aug_weight.test.js` (계산 쪽, 갈리오 · 방어 170 · 마저 65 · 체력 3450):

| 되돌리면 앞서 기억한 결과를 쓴다 (과잉 무효화 아님) | 0 → 450 → 0 에서 miss 0 이고 첫 결과와 같음 | ✔ (원래 통과) |

| 테스트 | 보는 것 | 수정 전 |

## 4. 조사 도구·문서 정정 (지적 1)

`docs/증강_가중치_연결표.md` 가 B1 수정 전 계산 경로를 그대로 적고 있었다. `tools/aug_weight_audit.js` 를 고쳐 다시 생성했다.

| 전 | 후 |
|---|---|
| `CRITSKILL → -` (가는 칸 없음) | `CRITSKILL → CRIT 몫 min(CRITSKILL,CRIT) 을 dps→combo 로` |
| 2.1절 "효과 성격이 다른데 전부 `dps`(평타) 칸" | 2.1절 "효과 성격별로 가는 칸" + 증강마다 실제로 가는 칸을 계산해 표기 |
| 2장 '스킬 치명타' 3개 → 태그 `CRIT` | '스킬 치명타' 4개 → 태그 `CRIT + CRITSKILL` |
| `APtoCRIT` 을 스킬 치명타로 분류 | 치명타 **확률**로 분류 (터지는 자리는 평타 — `CRITSKILL` 이 안 붙는다) |
| 효과식 치명타(쌍둥이 불꽃)를 평타 치명타로 분류 | 평타로 발동하지 않으면 스킬 치명타로 (`scaleTags` 와 같은 기준) |

분류 기준을 `web/scoring.js` 의 `SKILL_CRIT_KEYS`·`ATTACK_TRIGGER` 와 같은 값으로 맞춰, 다음에 코드만 고치고 도구를 안 고치는 일이 덜 생기게 했다.

## 5. 향후 개선 목록 (지적 2)

`docs/향후_개선_목록.md` 를 새로 만들어 6개를 적었다 — 이번 Phase 에서 **고치지 않았다.**

1. 스킬 치명타의 적용 범위 구분 (스킬 전부 / 지속 피해 / 아이템 효과 / 궁극기) — 지금은 세기가 전부 0.6
2. 챔피언별 스킬 피해와 평타 강화 스킬의 구분 (징크스 Q)
3. 회복·보호막·지원 효과로 성립하는 비정석 빌드 — B2 의 근거 게이트는 **피해 계산만** 본다. 회복·보호막 효과만 있는 증강 16개 중 8개는 그 계수가 반대 유형 능력치의 유일한 근거였다
4. 직접 지정된 `lift` 검증 — `rules.augments.*.lift` 가 있는 증강 3개(최첨단 발명가·퀸카·눈 오는 날)는 **전부 빈 객체**다. 의도인지 대조한 적 없다
5. 복수 증강 간 가중치·유형 필터 상호작용 — 지금 검증은 단일 증강 기준뿐
6. 아군 기여도 계산의 현재 범위 정리 — '아군 효과 없음'으로 범위 밖에 둔 3개(바람전달자의 축복·RISE·단체 포옹)와 이미 있는 지원 계산의 경계

## 6. 아직 확인하지 못한 것

1. **실제 게임 확인 0건** (0장 반복).
2. 회복량 추정 자체(`enemyTarget` 의 `selfHeal + vampHeal + itemSelfHp`)가 맞는지는 이번에 보지 않았다. 캐시가 그 값을 제때 반영하는지만 봤다.
3. 기준 상대의 **추가 체력(`BONUS_HP`)** 도 `setTarget` 으로 바꿀 수 있는데 여섯 열쇠에 없다. 지금 화면·게임 연동은 이 값을 바꾸지 않고(`enemyTarget` 이 돌려주지 않는다) 테스트 한 곳(`tests/item_effects.test.js`)에서만 쓰므로 당장 같은 증상은 안 난다. 같은 종류의 빠짐이라 적어 둔다 — 이번 Phase 범위(회복량)가 아니라 손대지 않았다.
4. 한 게임에서 회복량이 몇 번 바뀌는지 모른다. 바뀔 때마다 빌드 3종 ≈ 0.5초를 다시 쓴다.
