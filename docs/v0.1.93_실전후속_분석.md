## 1. 증강 기록 검증

### 1-1. 3176은 표시용이에요 (게임 데이터로 확인)

게임 원본(`.cache/kiwi.bin.json`)에서 펜타킬 증강 5개를 찾았어요.

| 번호 | 게임 안 이름 | 이름 문자열 키 | 스킬 증강 표시 | 스펠 |
|---:|---|---|---|---|
| 3170 | GoH_PentakillAug_Q (헤비) | `..._1_Name` | 있음 | 있음 |
| 3171 | GoH_PentakillAug_W (파워) | `..._2_Name` | 있음 | 있음 |
| 3172 | GoH_PentakillAug_E (스래시) | `..._3_Name` | 있음 | 있음 |
| 3173 | GoH_PentakillAug_R (둠) | `..._4_Name` | 있음 | 있음 |
| **3176** | **GoH_PentakillAug_Generic** | **`..._Generic_BlankName`** | **없음** | **내용이 빈 스펠** |

- 이름 문자열 키가 `BlankName`(빈 이름)이고, 연결된 스펠(`Augment_GoH_PentakillAug_Generic`)에 효과 데이터가 없어요.
- 모드 증강 목록(KIWI)에는 들어 있지만 **고르는 카드가 아니라 표시용**이에요.
- 그래서 **추천 데이터에 넣지 않아요.** 지금처럼 경기 결과 대조에서만 빼요(`desktop.py EOG_DISPLAY_NUMS`).
- 확인 안 된 번호를 임의로 추가하지 않는다는 원칙 그대로예요.

### 1-2. 칸 제한과 진짜 불일치를 나누는 설계

- 경기 결과의 증강 칸은 `playerAugment1~6` **여섯 개가 끝**이에요.
- 미스 포츈 판: 칸 6개가 3176(표시용) + 실제 증강 5개로 꽉 찼어요. 클릭 기록은 6개(+스래시), 기록 전에 고른 것까지 치면 7개예요. **칸이 모자라 두 개가 안 남았어요.**
- 지금은 이걸 전부 '다름'으로 적어요. 그래서 수집이 틀린 것처럼 보여요. **[오류: 비교 규칙]**

**제안 (구현 전):** 대조 결과를 셋으로 나눠요.

| 결과 | 조건 |
|---|---|
| 같음 | 클릭 기록과 경기 결과가 같음 |
| **칸 모자람** | 경기 결과 칸이 꽉 찼고(6개), 기록에만 있는 증강이 있고, 경기 결과에만 있는 증강은 없음 |
| 다름 | 그 밖 (경기 결과에만 있는 증강이 있거나, 칸이 비었는데 기록과 다름) |

- **재현 테스트:** 칸 6개가 꽉 찬 가짜 기록 + 클릭 7개 → '칸 모자람', 경기 결과에만 있는 증강이 있으면 '다름'. 기존 테스트(`test_python.py` tidy 관련 2개)는 그대로 둬요.

## 2. 누적형 증강 (극악무도)

### 2-1. 원인

- 규칙: `{"AP": {"dv": "APPerProc", "times": 60}}` → **스킬 적중 60번 가정**으로 주문력 60 고정. 근거는 "1분에 약 6번 × 10분"이에요. **[가정]**
- 실제(바드 판): 26초 0 → 81초 25 → 190초 94 → 891초 **115 안팎**. 초반엔 계산이 높고 후반엔 낮아요.

### 2-2. 영향 범위 (추천 결과)

같은 증강의 주문력 가정만 60 → 115로 바꿔 보면(실험, 적용 안 함):

| 챔피언 | 증강 효과 (맨몸 대비 %) 60회 → 115회 | 몰빵 빌드 |
|---|---|---|
| 럭스 | 43.4 → 83.2 (×1.92) | 바뀜 (내셔의 이빨 → 리치베인) |
| 바드 | 40.6 → 77.7 (×1.91) | 바뀜 (리치베인·폭풍 쇄도 → 새벽심장·월석) |
| 애니 | 46.2 → 88.6 (×1.92) | 순서 바뀜 |
| 베이가 | 34.9 → 66.8 (×1.91) | 그대로 |

- **가정 하나가 증강 가치를 두 배로 움직여요.** 173명 전원이 고를 수 있는 골드 증강이에요.
- 다만 **115는 한 판에서 나온 값**이라 그대로 쓸 근거가 못 돼요. 판마다 다르고, 적중 횟수는 챔피언·판 길이에 달려 있어요.

### 2-3. 역산을 쓸 수 있는지 검증 (바드 판 기록으로)

'실제 주문력 − 계산(증강 제외)'로 중첩을 역산해 봤어요. **아이템이 바뀌는 순간에 크게 흔들려요.**

| 시각 | 계산 | 실제 | 추정 중첩 | 비고 |
|---:|---:|---:|---:|---|
| 190초 | 60 | 94 | 94 | 안정 |
| 230초 | 160 | 103 | 3 | **아이템을 산 직후** (계산엔 들어갔고 게임 값엔 아직 없음) |
| 358초 | 160 | 207 | 107 | 안정 |
| 459초 | 250 | 241 | 51 | **아이템을 산 직후** |

→ **역산은 아이템·레벨이 바뀐 직후에는 쓰면 안 돼요.** 잠깐 켜지는 효과(바드 판 방어력·마법 저항력 +10, 공격 속도 +0.33)도 섞여요.

**제안하는 안전장치**

1. 관측할 능력치가 **하나뿐인** 증강에만 써요(극악무도 = 주문력).
2. 아이템·레벨이 바뀐 뒤 **일정 시간(예: 5초) 안의 값은 버려요.**
3. **서로 다른 두 번의 읽기에서 같은 값**이 나올 때만 반영해요(지금 '고른 증강 바로잡기'와 같은 방식, `PICK_CHECK_GAP`).
4. 결과는 **추정값으로 표시**해요(화면에 '게임 중 집계값으로 추정'). 정확한 중첩으로 확정하지 않아요.
5. 모루 능력치 추정(`trackAnvil`)과 **같은 능력치를 두고 다투지 않게** 해요. 모루 증강·모루 아이템이 있는 판에서는 역산을 끄는 게 안전해요.

## 3. 성장형 아이템 (윤 탈 야생화살)

### 3-1. 원인

- 설명: "공격 시 치명타 확률이 **영구적으로 최대 25%까지** 증가" (기본 치명타 0%).
- 우리 규칙: `{"CRIT": 0.25, "AS": 0.15}` + "치명타 중첩 최대 25%(풀로 쌓이는 걸 기준)". **18레벨 완성 빌드 기준으로는 맞는 가정이에요.**
- 실전(미스 포츈): 457초에 사고 → 실제 치명타 0 → 493초 0.01 → 532초 0.09 → 615초 0.24. **약 2분 반 동안 계산이 높아요.** 게임 중 '지금 능력치'와 다음 구매 추천에만 영향이 있어요.

### 3-2. 분리 제안

| 쓰는 곳 | 지금 | 제안 |
|---|---|---|
| 추천 점수(18레벨 완성) | 치명타 25% | **그대로** — 사자마자 낮다고 가치를 깎지 않아요 |
| 게임 중 '지금 능력치' 비교 | 치명타 25% | 성장 중인 능력치로 표시하고 **어긋남으로 세지 않아요** |
| 게임 중 다음 구매 | 치명타 25% | 관측값이 있으면 관측값 (없으면 가정값) |

- 방법은 이미 있는 구조를 그대로 써요: 아이템 규칙의 `uptime`(지금 능력치에서 빼는 칸)과 비슷한 **`ramp`** 칸을 두고, '지금 능력치'에서만 빼요. 추천 점수는 건드리지 않아요.
- **추천 가치가 낮아지지 않게** 하는 게 핵심이에요. 이번 변경은 '지금 능력치' 쪽만 건드려요.

### 3-3. 비슷한 아이템 조사

| 아이템 | 성장 조건 | 지금 계산 | 추천 빈도 |
|---|---|---|---|
| 윤 탈 야생화살 | 공격할수록 치명타 0 → 25% | 25% (완성 기준) | 균형 29/173 · 몰빵 561/3,038 |
| 탐욕의 군화 | 처치 관여당 모든 피해 흡혈 +0.6% (최대 10중첩) | **계산 안 됨** (기본 4%만) | 균형 0 · 몰빵 0 |
| 스테락의 도전 '잡아채는 발톱' | 추가 공격력 비례 | 계산 안 됨 (검증표에 이미 적힘) | 균형 3 · 몰빵 233 |

- 탐욕의 군화는 성장 몫(최대 +6%)이 계산에 없어요. 추천에 한 번도 안 들어가니 **영향은 작아요.** 같이 고칠지는 선택이에요.
