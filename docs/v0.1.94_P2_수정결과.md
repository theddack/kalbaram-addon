## 1. 클릭 우선순위 — 먼저 온 클릭

### 바꾼 것

`augocr.Tracker.click` 이 이번 선택 화면에서 **처음 온 클릭 하나만** 담아요.
예전엔 확실·짐작을 따로 모아 두고 확실을 늘 먼저 썼어요.

```python
if self._click is not None or self._guess is not None:
    return          # 이번 화면은 이미 정해졌다
if sure: self._click = slot
else:    self._guess = slot
```

확실·짐작 구분 자체는 **그대로 남겨 뒀어요** (어떤 근거로 잡았는지는 기록에 남아야 하니까).
바뀐 건 **순서를 본다**는 것뿐이에요.

### 왜 이게 맞나

`Tracker.click` 주석에 원래 적혀 있던 원칙이에요 — "카드는 누르는 순간 골라진다 → 처음 누른 카드.
그 뒤 클릭은 사라지는 카드 위를 누른 것". 지금까지는 이 원칙을 '확실끼리', '짐작끼리' 따로만 지켰어요.

### 테스트

| 테스트 | 내용 |
|---|---|
| `test_first_click_of_the_screen_wins` | 먼저 온 짐작 > 나중 확실 · 먼저 온 확실 > 나중 짐작 · 새로고침 전 짐작은 버림 |
| `test_pyke_guess_then_world_clicks` | 파이크 253초 그대로 (짐작 0번 → 1·2·2번 클릭) → **속전속결** |

## 2. 이름을 못 읽은 증강 — 미확정으로 보존

### 이미 되어 있던 것 (그대로 둠)

- `picked: None` 이면 화면이 선택지를 남기고 **'이걸로 선택'** 을 누르게 해요.
- 증강 칸으로 넓혀 찾기(`_recover`)가 돌아요 (`tries: 99`).
- 증강 칸이 보이면 잘못 잡은 것을 **스스로 바로잡아요** (`_settle_unverified`). — **손대지 않았어요.**

### 모자랐던 것

누른 칸(0번)을 알고 있는데 **그 정보를 버리고 있었어요.** 그래서 화면에는
'방금 고른 증강을 화면에서 확인하지 못했어요' 만 뜨고, 정작 누른 칸은 이름이 비어 있어
사용자가 고를 수도 없었어요.

### 바꾼 것

- `Tracker` 가 `pickedSlot`(누른 칸)을 같이 내보내요. 기록(`picked` 이벤트)에도 남아요.
- 화면 문구에 칸을 붙여요:
  > **왼쪽 칸은 새로고침한 뒤 이름을 못 읽었어요.** 방금 고른 증강을 화면에서 확인하지 못했어요. 고른 것의 **이걸로 선택**을 눌러 주세요.
- 이름은 **지어내지 않아요.** 새로고침 전 옛 이름으로 메우는 건 2026-10-20 신드라 판에서
  한 판 내내 틀린 원인이라 그대로 두었어요.
- 추천에는 그대로 안 들어가요 (`picked` 가 `None` 이라 예전과 같아요).

### 테스트

| 테스트 | 내용 |

| `test_rerolled_slot_clicked_before_name_read_keeps_slot` | 새로고침 → 이름 읽기 전 클릭 → `picked None` · `pickedSlot 0` · 안 누르고 닫히면 칸 없음 |
| `tests/ui.test.js` | 화면에 '왼쪽 칸은 새로고침한 뒤 이름을 못 읽었어요' 가 뜨고, 이름을 다 읽은 경우엔 안 뜸 |

## 4. `MAX_AUGMENTS = 4` 조사 — 영향 확인됨 (수정은 안 함)

### 코드에서 쓰이는 곳은 한 군데예요

`Reader._hud_every()` — 증강 칸을 **주기적으로** 다시 읽을 간격을 정해요.

```python
if soon or self._verify or self._recover: return 2      # ← 고른 직후 확인은 여기서 먼저 걸린다
if len(self.hud_ids) >= MAX_AUGMENTS:     return inf     # 4개를 찾았으면 주기 읽기를 멈춘다
```

- **고른 직후 확인과 넓혀 찾기는 영향을 안 받아요.** 첫 줄이 먼저 걸려요.
- `_apply_hud`·`resolve_groups`·`_settle_unverified` 어디에도 4개 상한은 없어요.
- 추천에 넘기는 증강 수는 화면 쪽 `AUG_MAX = 6` 이라 5·6번째도 들어가요.

### 그런데 증강 칸 목록 자체가 4개를 못 넘어요 — 기록으로 확인

7판 전부에서 증강 칸(HUD) 목록이 **한 번도 4개를 넘지 않았고**, 5개 이상 고른 두 판에서는
새 증강이 들어올 때 **먼저 찾았던 증강이 빠졌어요.**

| 판 | 기록한 고르기 | 증강 칸 최대 | 빠진 적 |
|---|---:|---:|---|
| 바드 | 4 | 4 | 1회 (일시적) |
| **미스 포츈** | **6** | **4** | **4회** — 550.3 조준경 부착 빠짐 · 842.4 과충전 빠짐 |
| 베인 | 3 | 3 | 0 |
| **그레이브즈(23:36)** | **5** | **4** | **1회** — 764.1 불을 밝혀 빠짐 |
| 그레이브즈(23:53) | 4 | 3 | 0 |
| 파이크 | 4 | 4 | 0 |
| 케이틀린 | 4 | 4 | 0 |

### 무슨 영향이 있나

1. **확인이 헛돌아요.** 맞게 고른 증강인데 칸에서 안 보이면 `verify` 가
   '증강 칸에서 못 찾음' 으로 끝나고 `_unverified` 로 넘어가 넓혀 찾기까지 돌아요 (CPU 낭비).
2. **잘못 바로잡을 수 있어요(아직 사례 없음).** `_settle_unverified` 는
   '같은 선택지 중 다른 증강 하나가 칸에 새로 나타나면 그걸로 고친다' 예요.
   칸 목록이 불안정하면 이 조건이 엉뚱하게 맞을 수 있어요. **7판에서는 한 번도 안 일어났어요**
   (딱 한 번 동작한 미스 포츈 11.1초는 맞게 고쳤어요).
3. 4개를 찾은 뒤에는 주기 읽기가 멈춰서, 고르기 사이에 생긴 어긋남을 다시 볼 기회가 없어요.

### 수정안 (승인 전까지 안 해요)

| 안 | 내용 | 장단점 |
|---|---|---|
| **A. 상한을 '그 판에 고른 수'로** | `MAX_AUGMENTS` 고정값 대신 `max(4, len(self._picked_names))` | 기록으로 뒷받침돼요. 고른 수가 늘면 주기 읽기를 계속해요. 읽기 횟수가 늘어 CPU 가 조금 더 들어요 |
| **B. `_settle_unverified` 에 안전장치** | 칸 목록이 **줄어든 직후**에는 바로잡지 않기 | 2번 위험만 막아요. '줄어든 직후'를 판단할 기준이 필요해요 |
| **C. 그대로 두고 기록만** | 지금 상태 | 1·3번이 남아요. 실제로 틀린 기록이 생긴 사례는 아직 없어요 |

**추천: A 를 먼저 재 보기.** 다만 증강 칸 읽기는 CPU 를 가장 많이 쓰는 작업이라
(`HUD_EVERY`·`HUD_GIVE_UP` 주석), **성능을 같이 재고 나서** 결정하는 게 맞아요.
B 는 '줄어든 직후' 기준이 지어낸 값이 되기 쉬워요.

**왜 칸이 4개를 못 넘는지는 아직 몰라요.** 게임 화면이 4개까지만 보여 주는 건지,
우리 쪽 아이콘 자리(`_slot_ids`) 때문인지 기록만으로는 못 갈라요. A 를 넣기 전에 이것부터 봐야 해요.

## 8. v0.1.94 배포 가능 여부

**계산 쪽은 영향이 없고(추천 기준선 변화 0), 인식 쪽은 7판 기준 3 → 5판으로 나아졌어요.**
