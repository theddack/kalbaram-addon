# 상대 정보 → 추천 연결표

v0.1.95 Phase 4-1 조사 · 2026-11-25 · 코드 기준: `web/app.js` · `web/stats.js` · `web/scoring.js`
**현재 적용 상태 (2026-11-25 갱신)**: C1(상대 회복량에서 보호막 분리) · C2(상대 추가 체력 연결·갱신 조건) · E1·E2(자기/아군 회복·보호막 분리) · C9-A1·A2·A2.5(저항 감소 공통 계산 순서·합치기 규칙·중첩 평균 식) **적용됨**. 저항 감소는 **자리만 만들었고 아이템은 아직 연결하지 않았다** (C9-A4 승인 대기).
그 밖의 항목은 **조사 결과일 뿐 아직 코드에 없다**. 표의 각 줄은 '지금 코드가 그러하다'를 뜻한다.

> 게임이 알려 주는 상대 정보가 **추천 계산에 실제로 들어가는지**를 항목마다 가른 표예요.
> 코드와 데이터를 읽어 적은 것이고 실제 게임 결과가 아니에요.

## 0. 먼저 — 계산에 들어가는 상대 값은 여섯 개뿐이다

추천 계산(`Stats.evaluate` → `Scoring`)이 보는 상대 값은 **전역 기준 상대 `Stats.TARGET` 다섯 개 + `statOpts.enemyMagic` 하나**가 전부다.
(C2 전에는 다섯 개였다 — `BONUS_HP` 가 늘 기본값이라 실제 상대에서 들어오는 값이 네 개뿐이었다.)

| 값 | 실제 상대에서 들어오나 | 들어오는 곳 |
|---|---|---|
| `TARGET.ARMOR` | ✔ | `app.js enemyTarget()` — 적 5명 18레벨 예상 평균 |
| `TARGET.MR` | ✔ | 〃 |
| `TARGET.HP` | ✔ | 〃 |
| `TARGET.HEAL` | ✔ | 〃 (`selfHeal + vampHeal + itemSelfHeal` 평균, v0.1.95 C1 전에는 `itemSelfHp` — 보호막까지 섞여 있었다) |
| `TARGET.BONUS_HP` | ✔ (v0.1.95 C2 부터) | 〃 (적 5명 추가 체력 평균). **정정 2026-11-25**: 앞서 이 자리에 "`setTarget` 도 안 받는다"라고 적었는데 틀렸다. `setTarget` 은 `bonusHP` 를 처음부터 받고 있었고(`stats.js:467`, `tests/item_effects.test.js` 가 이미 그렇게 쓴다) **`enemyTarget()` 이 안 돌려주는 것만이 원인**이었다 (C2 수정안 설명이 맞다). C2 전에는 늘 기본값 300 |
| `TARGET.CUR` (현재 체력 비율) | ✖ | 항상 0.7 고정 |
| `TARGET.DPS_TAKEN` (받는 피해 초당) | ✖ | 항상 600 고정 |
| `statOpts.enemyMagic` | ✔ | `app.js:14` — 적 챔피언 유형·산 아이템·킬로 짐작, 반영 60% (0.2~0.8) |

그 밖의 상대 정보(보호막·공격 속도·군중 제어·폭딜·지속 피해 …)는 **계산에 전달되는 통로 자체가 없다.**
있는 것은 `enemyAdvice()` 가 만드는 **조언 문구**와, 그 문구가 미는 후보 목록(`state.adviceWant` / `state.adviceNeed`)뿐이다.
> **(2026-11-26 v0.1.95 Phase 4 C5 로 바뀜)** `state.adviceWant` 와 '다음 구매 3번째 자리 강제 삽입'은 없앴다.
> 계산되는 대응(치유 감소·관통·저항)은 점수가 올리고, 계산 밖 대응은 조언 줄에 `계산에는 안 들어감(참고)` 으로만 남는다.
> `state.adviceNeed`(6칸 바꾸기)에도 계산되는 대응만 들어간다. 아래 본문의 서술은 **고치기 전** 기준이다.

## 2. 추천 경로별 차이

여덟 갈래 모두 같은 `statOpts()` 와 같은 전역 `Stats.TARGET` 을 쓴다. **계산 기준이 갈라지는 곳은 없다.**
차이는 '기준 상대와 비교하느냐'뿐이다.

| 추천 | 함수 | 기준 상대(기본값)와 따로 비교하나 |
|---|---|---|
| 아이템 개별 추천 | `itemRanking()` → `S.rankItems` | 아니오 (지금 상대 기준만) |
| 다음 구매 | `renderNextBuy()` → `S.buyNowGains` | 아니오 |
| 균형·공격 집중·그 밖 빌드 | `renderBuild()` → `S.buildConcepts` | 아니오 |
| 상대 대응 아이템 | `counterItems()` | **예** — `atDefault()` 로 기준 상대 순위를 또 내서, 순위가 `COUNTER_UP` 이상 오른 것만 뽑는다 |
| 구매한 아이템 평가 | `itemVerdicts()` | 아니오 |
| 증강 추천·연계 등급 | `getTiers()` → `S.augmentTiers` | 아니오 |
| 증강 카드 (게임 중) | `app.js:1287` | **예** — 기준 상대 대비 증강 이득 차이를 따로 낸다 |
| 능력치 패널 '지금 수치' | `withNowTarget()` | 상대를 **지금 레벨·산 아이템만**으로 바꿔 계산 (회복량은 예상 상대 값 그대로) |

즉 **'상대 대응'은 따로 계산하는 게 아니라, 같은 계산을 두 기준(기준 상대 ↔ 이번 판 적)으로 돌려 순위가 오른 아이템을 뽑는 방식**이다.
그래서 §1 에서 ③·④·⑥ 로 분류된 정보는 '적 대응' 목록에도 끝내 나타나지 않는다 — 두 기준 사이에서 값이 하나도 안 변하기 때문이다.

## 3. 바로 드러난 어긋남

1. **문구와 계산의 기준이 다르다** — '적 회복 많음' 문구는 아군 회복 스킬까지 세고(`heals(c) >= 2`), 치유 감소 아이템 점수는 적의 **자기** 회복만 본다(`TARGET.HEAL`). 소라카가 있어도 `TARGET.HEAL` 은 안 오른다.
2. **문구가 미는 아이템을 계산이 안 받쳐 준다** — 보호막 감소·강인함·군중 제어 해제·공속 대응은 계산 키가 없거나(`독사의 송곳니`·`헤르메스의 시미터`) 상대와 무관한 근사(`ehpPhysMult`)다. 그런데 `state.adviceWant` 를 타고 다음 구매 3번째 자리에 들어간다.
3. **추가 체력이 통로에서 끊겨 있었다** — `tgtBonusHpAmp` 는 `TARGET.BONUS_HP` 를 읽는데 `enemyTarget()` 이 그 값을 안 돌려줬다 (`setTarget` 쪽은 처음부터 받고 있었다). **v0.1.95 Phase 4 C2 에서 연결했다.**
4. **`TARGET.HEAL` 이 보호막을 회복으로 센다** — `itemSelfHp` 가 아이템의 자기 회복과 자기 보호막을 한 통에 담는다(`stats.js:788`). 고통스러운 상처는 보호막을 못 깎는데 치유 감소 점수가 오른다. 실제 기록 5판에서 잰 몫은 `docs/v0.1.95_Phase4_상대정보_조사.md` §3 에 있다.
