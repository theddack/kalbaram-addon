## 0. 지금 코드가 하는 일 (사실 확인)

```js
// web/stats.js:445 — 수정 전 (C9-A1 적용 전) 코드
function mitigation(resist, pctPen, flatPen) {
  const eff = Math.max(0, resist * (1 - pctPen) - flatPen);
  return 100 / (100 + eff);
}
// web/stats.js:607-608
const physMit = mitigation(TARGET.ARMOR, t.ARPEN, t.LETHALITY) * …
const magMit  = mitigation(TARGET.MR * (1 - Math.min(0.9, cv.mrShred || 0)), t.MPENP, t.MPEN) * …
```

|---|---|
| 비율 **마법 저항력** 감소 | `cv.mrShred` 하나뿐. 쓰는 데이터는 **핏빛 저주 1개**(0.1125) |
| 비율 **방어력** 감소 | **계산 키가 아예 없다** (`armorShred` 를 읽는 코드가 없음) → 칠흑의 양날 도끼 6%×5중첩 미계산 |

## 1. 적용 순서 (원본 확인)

위키 기준 순서는 **① 고정 감소 → ② 비율 감소 → ③ 비율 관통 → ④ 고정 관통(치명)** 이다
([Armor penetration](https://wiki.leagueoflegends.com/en-us/Armor_penetration) ·
[Magic penetration](https://wiki.leagueoflegends.com/en-us/Magic_penetration) · [Armor](https://wiki.leagueoflegends.com/en-us/Armor)).
고정 감소는 추가 저항부터 깎고 그다음 기본 저항을 깎는다. 비율 **관통**은 저항이 0 이하면 아무 일도 안 한다.
저항 **감소**는 0 아래로 내릴 수 있지만, 이 순서 때문에 실제로 음수가 되는 일은 거의 없다고 위키 자신이 적고 있다.

→ 지금 코드의 `mitigation(MR × (1 − mrShred), MPENP, MPEN)` 은 ②③④ 순서로는 **맞다**. 빠진 것은 ① 하나다.
→ 그러므로 공통 규칙은 `mitigation(resist, pctPen, flatPen, pctRed, flatRed)` 한 군데만 늘리면 된다.

```
eff = max(0, ((R − flatRed) × (1 − pctRed)) × (1 − pctPen) − flatPen)
```

  방어력 감소(깎아내기)는 **6초·5중첩**이라 *켜짐/꺼짐*이 아니라 **몇 중첩이 쌓여 있나**의 문제다.
  → 가동률이 아니라 **중첩 평균**으로 재야 한다 (핏빛 저주와 같은 방식).
- **악의의 고정 마법 저항력 감소는 상시가 아니다.** 조건이 **궁극기 적중**이고 지속이 **3초**다.
  → `ultUptime(3)` = `min(1, 3 / 궁극기 재사용 대기시간)` 꼴로 재야 한다. 이 헬퍼는 `stats.js:631` 에 이미 있다
  (존야·궁 발동 효과가 쓰는 것과 같은 자리).

### 중첩 도달 속도 — 계산 규칙 제안

중첩형은 모두 같은 꼴이다: **한타 동안 쌓는 속도 × 지속시간 → 평균 중첩**.

```
쌓는 횟수/초  r = (평타 r_auto = 공격 속도) 또는 (스킬 r_skill = 콤보 스킬 수 ÷ 콤보 시간)  ← 조건(on)에 따라 고름
포화 중첩     s* = min(최대 중첩, r × 지속)
평균 중첩     s̄ = s* × (1 − 포화까지 걸린 시간 ÷ 한타 시간)  … 램프 구간 보정 (한타 AUTO_FIGHT_SEC = 6초)
값           = 중첩당 값 × s̄
```

이 식 하나로 칠흑(물리 피해 → 평타+스킬, 6초, 5중첩), 핏빛 저주(스킬 마법 피해, 6초, 4중첩),
부식(모든 피해, 4초, 20중첩)이 **같은 규칙**으로 풀린다. 지금 세 개가 각각 다른 가정값
(75% 가동률 / 중첩 평균 1.5 / 평균 10중첩)으로 손으로 적혀 있는 것을 이 규칙으로 대체한다.

> 램프 보정 항은 **가정**이다 (근거 자료 없음). 지금 쓰고 있는 세 가지 가정값도 전부 `noData: true` 라,
> 가정을 없애는 게 아니라 **가정을 한 군데로 모으는** 변경이다.

- **같은 아이템 두 개**: 데이터의 `limit` 필드가 막는다 (칠흑 `"Fatality"`, 핏빛 저주 `"Blight"`). 이미 있는 장치다.

  지금 `conv.mrShred` 는 **더한다**. 출처가 핏빛 저주 하나뿐이라 지금은 틀린 값이 나오지 않지만,
  칠흑·부식·나서스를 같이 넣으면 그 순간부터 과대평가가 된다.
  → 공통 규칙에서 `PCT_PEN` 과 같은 방식(`1 − (1−a)(1−b)`)으로 합쳐야 한다. 고정 감소는 더한다.
- **감소와 관통**: 서로 다른 단계라 둘 다 적용된다 (1절 순서).

## 4. 챔피언 스킬의 저항 감소 — 지금은 조사 경로가 없다

`web/data.json` 의 챔피언 스킬에는 **설명 문장이 들어 있지 않다** (`spells[].desc` 가 전부 `null`).
그래서 "스킬로 저항을 깎는 챔피언이 몇 명인가"를 지금 데이터로는 셀 수 없다.
처음에 자동 검색으로 "0명"이 나왔는데 그건 **효과가 없다는 뜻이 아니라 원본 문장이 없다는 뜻**이다 — 정정한다.

실제로 나서스 E(영혼의 불길)는 **대상 방어력 30~50% 감소**가 맞다
([Nasus](https://wiki.leagueoflegends.com/en-us/Nasus) · [Data Nasus/Spirit Fire](https://wiki.leagueoflegends.com/en-us/Template:Data_Nasus/Spirit_Fire),
다만 위키 본문 쪽이 오래되어 해당 패치 값은 따로 확인이 필요하다).
아이템만 고치고 챔피언 쪽을 비워 두면 "칠흑은 세는데 나서스 E 는 안 센다"가 되므로,
**공통 규칙의 키는 챔피언 스킬에서도 쓸 수 있는 이름**으로 둔다 (`champions` 규칙에서 같은 키를 읽게).
챔피언 스킬 원본 문장을 넣는 일 자체는 **C7·Phase 5A 와 같은 '원본 데이터 경로' 문제**라 그쪽에 묶는다.

## 5. 저항 감소로 아군이 더 넣는 피해

관통은 **나만** 득을 보고, 저항 감소는 **그 대상을 때리는 모두**가 득을 본다. 이게 둘의 진짜 차이다.
지금 모델에는 이 통로가 없다. 다만 **새 모델이 필요하지는 않다** — 기준 아군 `ALLY`(`stats.js:460`)가 이미 있고
`allyGain()` 이 '아군이 더 넣는 피해'를 체력 단위로 바꾸는 자리도 있다.

```
allyShredGain = (ALLY.autoDps + ALLY.skillDps) × (감소 후 피해배율 ÷ 감소 전 피해배율 − 1) × 지속 몫 × 아군 수
```

- 아군 수는 지금의 **1명** 규칙을 그대로 쓴다 (회복·보호막·아군 강화와 같은 기준, `ALLY_TARGETS`).
- 이건 C8(받는 피해 분포)이나 C4(아군 회복)와 **다른 종류의 확장이 아니다**. 기존 ALLY 모델로 바로 된다.
- 그래도 **C9 본체와는 분리**한다. 저항 감소를 내 피해에 반영하는 것(C9-A)과
  아군 몫까지 더하는 것(C9-B)은 영향 범위가 다르고, C9-B 는 지원 지표 쪽 가중치를 건드린다.

# 7. 보완 (2026-11-25, 지적 3)

## 7.1 평균 중첩 식 — 쌓는 동안의 효과가 빠져 있었다

앞 2절에 적은 `s̄ = s* × (1 − 포화까지 걸린 시간 ÷ 한타 시간)` 은 **틀렸다**.
그 식은 쌓는 구간을 통째로 0 으로 치고, 포화 시간이 한타보다 길면 **음수**가 된다 (예: 부식 20중첩).
쌓는 구간에도 중첩은 선형으로 올라가므로 그 구간의 평균은 **절반**이다. 적분해서 다시 쓰면:

```
r   = 쌓는 횟수/초 (조건 on 에 따라 평타 공격 속도 · 스킬 빈도 · 둘의 합)
s*  = min(최대 중첩, r × 지속)      … 포화 중첩
t_r = s* / r                        … 포화까지 걸리는 시간
T   = 한타 시간 (AUTO_FIGHT_SEC = 6)

t_r ≤ T :  s̄ = s* × (1 − t_r / (2T))        … 앞은 평균 s*/2, 뒤는 s*
t_r > T :  s̄ = min(s*, r × T / 2)           … 한타 내내 쌓기만 한다
```

- **항상 0 ≤ s̄ ≤ s\*** 다. 음수가 나올 수 없다 (지적 3-②).
- 쌓는 동안의 몫이 `s*/2 × t_r/T` 로 들어간다 (지적 3-①).
- 검산: 칠흑(6% ×5, 6초, r≈1.5/초) → s\* = min(5, 9) = 5, t_r = 3.3초 → s̄ = 5 × (1 − 0.28) = 3.6 → 21.6%.
  부식(1.5% ×20, 4초, r≈2/초) → s\* = min(20, 8) = 8, t_r = 4초 → s̄ = 8 × (1 − 0.33) = 5.3 → 8.0%
  (지금 규칙의 '평균 10중첩 = 15%' 보다 낮다 — **이 차이는 가정이 아니라 식에서 나온다**).

**발동 횟수가 0 인 경우 (2026-11-25 추가 지적)**: `r = 0` 이면 `s* = 0` 이고 `t_r = s*/r = 0/0 = NaN` 이 된다.
그러면 평균도 NaN 이 되어 피해 배율 전체가 NaN 으로 번진다. 그래서 **쌓을 수 없는 조합은 식을 타기 전에 0 으로 끊는다**:

```
r ≤ 0  또는  지속 ≤ 0  또는  최대 중첩 ≤ 0   →   s̄ = 0   (값도 0)
```

해당하는 실제 경우: ⑴ 평타로 쌓는 효과인데 평타를 안 치는 가정(`EXP.autoUptime = 0`),
⑵ 스킬로 쌓는 효과인데 그 스킬이 없는 챔피언(`flags.noUlt` 로 궁이 막힌 증강 포함), ⑶ 데이터에 지속·최대 중첩이 안 적힌 효과.

**적용 상태 (C9-A2.5, 적용됨)**: `web/stats.js` `shredExpect({ perStack, maxStacks, rate, dur, fightSec, pinnedAvg })`.
`pinnedAvg` 를 주면 그 중첩 평균을 그대로 쓴다 — 핏빛 저주는 기존 가정 **1.5 를 고정**해 두어 값이 `0.1125` 그대로다.
테스트로 두 갈래 손 계산, 발동 0회 5가지, `0 ≤ 평균 ≤ 포화 중첩`(100조합)을 고정했다 (`tests/calc.test.js`).
~~아직 어떤 아이템도 이 함수를 쓰지 않는다~~ → **C9-A3 에서 핏빛 저주가 이 함수를 탄다** (8절). 새 효과 연결은 C9-A4.

## 7.2 악의 — 한타 안 가동률과 긴 가동률을 따로 센다

`ultUptime(dur) = min(1, dur ÷ 궁 재사용 대기시간)` 은 **여러 한타를 평균한 긴 가동률**이다.
한타 한 번만 보면 궁은 보통 한 번 들어가고, 그때부터 3초 동안만 마법 저항력이 깎인다.

| 재는 것 | 식 | 쓰는 데 |
|---|---|---|
| 한타 안 가동률 | `min(1, 3초 ÷ AUTO_FIGHT_SEC)` = 0.5 | **저항 감소**(콤보 피해에 곱) |
| 긴 가동률 | `ultUptime(3)` = `3 ÷ 궁 재사용 대기시간` | 초당 피해(DPS) 쪽 |
| 장판 지속 피해 | 지금처럼 `effects` 의 `once` (콤보 1번에 1번) | 그대로 둔다 |

→ 셋을 한 값으로 묶지 않는다. 저항 감소에는 **한타 안 가동률**을 쓰고, 장판 피해 가정은 건드리지 않는다.

**중복 적용 방지 규칙 (2026-11-25 추가 지적)**. 두 가동률을 곱하면 같은 '궁을 쓴다'는 사실을 두 번 깎는다.
그래서 **한 값에는 한 가동률만** 쓰고, 어느 쪽을 쓸지는 **그 값이 재는 시간 단위**로 정한다:

| 값이 재는 것 | 쓰는 가동률 | 왜 |
|---|---|---|
| 한타 한 번의 피해 (콤보·저항 감소) | 한타 안 가동률 `min(1, 3 ÷ 한타 6초)` = 0.5 | 한타 한 번 안에서 궁은 보통 한 번, 그 3초만 깎인다 |
| 긴 시간 평균 피해 (초당 피해) | `ultUptime(3)` = `3 ÷ 궁 대기시간` | 여러 한타를 평균한 값 |
| 장판 지속 피해 | 지금처럼 `effects` 의 `once` | 건드리지 않는다 |

- **곱하지 않는다.** `한타 안 가동률 × 긴 가동률` 은 쓰지 않는다 (앞 판에 그렇게 적었던 것을 **정정**한다).
- 궁 대기시간이 한타보다 긴 챔피언은 **긴 가동률 쪽에서만** 낮게 나온다. 한타 피해는 '궁을 쓴 한타'를 재는 값이므로 그대로 둔다.
- 코드에서 섞이지 않게 **키를 나눈다**: 저항 감소 쪽은 `fightUptime`, 초당 피해 쪽은 기존 `ultUptime`.
  같은 효과가 두 키를 동시에 쓰면 테스트로 실패하게 만든다 (C9-A4 범위).

## 7.3 음수 저항력과 관통 적용 조건

| 규칙 | 게임 | 1차 구현 |
|---|---|---|
| 저항 **감소**는 0 아래로 내려간다 | 음수 저항이면 피해 배율 `2 − 100/(100 − R)` | **0 에서 자르는 지금 방식을 유지**한다 |
| 비율 **관통**은 저항이 0 이하면 아무 일도 안 한다 | 곱하기라서 | 순서상 자동으로 그렇다 |
| 고정 관통은 0 아래로 못 내린다 | | `Math.max(0, …)` 그대로 |

**이 결론의 범위 (2026-11-25 명시)**. '음수 저항은 생기지 않는다' 는
〈2026-11-17 빌드 데이터(16.22.1) · 저항 감소 효과가 핏빛 저주 하나 · 아군 몫 미연결〉 **지금 범위에서만** 성립한다.
C9-A4(칠흑·악의) · A5(부식) · B(아군 몫) 를 붙이면 감소와 관통이 겹치므로 **그때 다시 재고**,
클램프가 실제로 걸리는 장면이 하나라도 생기면 그 시점에 보고한다 (`tools/c9_shred_check.js` 의 마지막 절이 그 측정이다).

음수 영역을 넣으면 **지금 결과가 움직인다**. 그래서 1차에는 자르는 방식을 두고,
**음수가 실제로 생기는 조합이 있는지를 먼저 측정해 보고한다** (고정 감소가 악의 10 하나뿐이라 안 생길 것으로 본다).
측정에서 생긴다면 그때 음수 구간을 별도 승인 항목으로 올린다.

## 7.4 아군 몫은 물리·마법을 갈라야 한다

방어력 감소는 아군의 **물리** 피해만, 마법 저항력 감소는 **마법** 피해만 키운다.
지금 기준 아군 `ALLY` 에는 **피해 유형 비중이 없다** (원딜 29명의 중앙값인데 물리/마법 몫이 안 적혀 있다).

```
allyShredGain(armor) = ALLY 물리 피해 × (감소 후 ÷ 감소 전 − 1) × 한타 안 가동률 × 아군 수(1)
allyShredGain(mr)    = ALLY 마법 피해 × (〃)
```

### C9-B0 측정 결과 (2026-11-25, 조사 끝)

`tools/ally_damage_mix.js` 로 쟀다. 피해는 저항 계수에 대해 **1차식**이라 (`D = 물리몫 × physMit + 마법몫 × magMit + 고정몫`),
기준 상대의 방어력·마법 저항력을 번갈아 아주 크게(1e6) 만들어 유형별로 갈라냈다.
재는 값은 **방어 적용 뒤 실제로 들어가는 피해**의 비중이고, 조건은 `tools/ally_model.js` 와 같다 (18레벨 균형 빌드·증강 없음).

| 무리 | 물리 | 마법 | 고정 | 갈라낸 합과 실제 피해의 차이 |
|---|---|---|---|---|
| **기준 아군 = 원거리 딜러 29명** | **98.6%** | **1.4%** | 0.0% | 중앙값 0.0% (가장 큰 사미라도 0.0%) |
| 참고: 메이지 35명 | 12.8% | 87.2% | 0.0% | 0.0% |
| 참고: 전 챔피언 173명 | 57.7% | 34.2% | 0.0% | 0.0% |

**중앙값 합이 100% 가 아닌 이유 (2026-11-25 보완)**: 세 비중을 **각각 따로** 중앙값 낸 값이라
물리 중앙값을 만든 챔피언과 마법 중앙값을 만든 챔피언이 다르다 (전 챔피언 합 92.0%).
챔피언 한 명 안에서는 언제나 100% 다 (분해 오차 0.0%). 합이 맞는 평균은
원딜 **물리 92.0 · 마법 8.0**, 전 챔피언 **물리 58.8 · 마법 40.0 · 고정 1.2** 다.
따라서 **'유형을 안 가르면 약 70배 과대평가' 는 중앙값(1.4%) 기준**이고, 평균(8.0%) 기준으로는 약 12배다.
결론(유형을 갈라야 한다)은 같지만 배수는 기준에 따라 다르다.

(지표마다 따로 낸 중앙값이라 가로 합이 100% 가 아니다. 원딜 중 마법 비중이 큰 쪽은 티모 85.6% · 진 42.2% · 코그모 36.6%,
0% 쪽은 자야·퀸·트위치다.)

**C9-B 에 미치는 결론**

- **방어력 감소(칠흑)의 아군 몫은 거의 전부 살아 있다** (기준 아군 피해의 98.6%).
- **마법 저항력 감소(핏빛 저주·악의)의 아군 몫은 기준 아군에선 1.4% 뿐이다.** 유형을 가르지 않고 아군 몫을 더하면
  핏빛 저주의 아군 득이 **약 70배로 부풀려진다**. 지적하신 과대평가가 수치로 확인됐다.
- 그래서 C9-B 식은 아래처럼 **유형별로 따로** 쓴다. 비중은 `ALLY` 에 `pPhys 0.986` · `pMag 0.014` 로 적어 둔다
  (아군이 메이지라는 가정은 넣지 않는다 — 지금 아군 모델이 원딜 1명이라는 기존 가정을 그대로 따른다).

```
allyShredGain(방어력) = (ALLY.autoDps + ALLY.skillDps) × ALLY.pPhys × (감소 후 physMit ÷ 감소 전 physMit − 1) × 한타 안 가동률 × 아군 수(1)
allyShredGain(마저)   = (ALLY.autoDps + ALLY.skillDps) × ALLY.pMag  × (감소 후 magMit  ÷ 감소 전 magMit  − 1) × 〃
```

→ C9-B0 은 **조사까지 끝났고 코드에는 아직 넣지 않았다** (`ALLY` 에 비중을 적는 것부터가 C9-B 범위, 승인 대기).

## 7.5 부식 — 관통에서 빼는 것과 감소로 넣는 것을 한 커밋으로

## 7.6 핏빛 저주 값이 왜 바뀌는지 가른다

지금 `mrShred 0.1125` 는 **가정값**(중첩 평균 1.5 × 7.5%)이고, 새 식은 중첩 평균을 계산으로 낸다.
값이 바뀌면 원인이 둘로 섞이므로 **두 단계로 나눠 검증**한다.

1. **식만 넣고 중첩 평균을 1.5 로 고정** → 결과가 **한 치도 안 바뀌는지**(항등) 테스트로 확인.
2. 그 다음 중첩 평균을 식에 맡긴다 → 바뀐 값과 **그 원인(스킬 빈도 r, 지속 6초, 최대 4중첩)**을 수치로 적는다.

이렇게 하면 "식 때문인지 가정 때문인지"가 섞이지 않는다.

## 7.7 검증 기준 교체 (지적 3 마지막)

'상대 방어력이 높을수록 칠흑 점수가 반드시 오른다'는 **단조성 기준을 버린다** (점수는 다른 항목과 섞여 정해져서
그 자체로는 계산이 맞는지 못 말해 준다). 대신 **계산식과 바로 대조**한다.

| 검증 | 기대값 |
|---|---|
| 저항 감소량 | 방어력 R, 비율 감소 s, 고정 감소 f → `유효 저항 = (R − f) × (1 − s)` 와 일치 |
| 피해 변화 | `피해 증가율 = (100 + R) ÷ (100 + 유효 저항) − 1` 와 일치 (손 계산과 소수점까지) |
| 순서 | 고정 감소 → 비율 감소 → 비율 관통 → 고정 관통. 순서를 바꿔 넣으면 값이 달라지는 것까지 테스트로 고정 |
| 중첩 평균 | 7.1 식의 두 갈래(포화 전·후)를 각각 손 계산과 대조 |
| 아군 몫 | 7.4 식과 일치, 물리·마법을 바꿔 넣으면 0 이 되는 것 확인 |

# 8. C9-A3 적용 (2026-11-26) — 공통 계산 연결

## 8.1 무엇을 연결했나

규칙에 **숫자로 적어 두던** 저항 감소를 **'쌓이는 방식'** 으로 적고, 엔진이 챔피언마다 풀게 했다.

```json
"핏빛 저주": {"stats": {"_shred": [
  {"stat": "mrShred", "perStack": 0.075, "maxStacks": 4, "dur": 0, "on": "skill", "pinnedAvg": 1.5}]}}
```

| 자리 | 하는 일 |
|---|---|
| `rules.json` `_shred` | 깎는 능력치(`stat`) · 중첩 하나가 깎는 양 · 최대 중첩 · 한 중첩이 남는 시간 · 쌓는 방법(`on`) · 중첩 평균 고정값 |
| `web/stats.js` `computeStats` | 숫자가 아니라 **규칙 그대로** 모아 둔다 (`conv._shreds`) — 쌓는 속도는 챔피언마다 다르다 |
| `web/stats.js` `metrics` | 공격 속도·시전 빈도로 **쌓는 속도**를 내고 `shredExpect()` 로 평균 중첩 → 값 (`out.shred`) |
| `build_data.py` · `tools/rules_patch.py` | `_shred` 는 게임 데이터 이름이 아니므로 **그대로 통과**시킨다 (두 빌드 경로 모두) |

## 8.2 지킨 것 (지적한 순서대로)

| 확인 | 어떻게 |
|---|---|
| 중첩당 감소량·최대 중첩·발동 빈도·지속시간·전투시간을 **구분** | 모두 따로 적는다. 전투시간은 공통 가정(`AUTO_FIGHT_SEC` 6초) |
| 중첩 **형성 시간**과 **유지 시간** 반영 | `shredExpect` 의 두 갈래 식 (7.1) — 쌓는 구간 평균은 절반 |
| 중첩 기대값에 **이미 들어간 가동률을 다시 곱하지 않음** | 쌓는 속도(rate)는 `shredRate()` 한 자리에서만 정하고, 바깥에서 곱하는 자리가 없다 |
| 발동 빈도 0 · 지속시간 0 · 최대 중첩 도달/미도달 | 앞 세 가지는 식을 타기 전에 0 으로 끊는다. 도달은 포화 중첩 상한, 미도달은 쌓는 중 평균 (단위 테스트) |
| **핏빛 저주 값 불변** | `pinnedAvg: 1.5` → 0.075 × 1.5 = 0.1125. 챔피언 173명 전부 같은 값 |
| 물리·마법 **적용 경로 분리** | `armorShred`/`armorFlatShred` 와 `mrShred`/`mrFlatShred` 를 따로 모아 각 `mitigation()` 에 넣는다 (섞이면 깨지는 테스트) |
| 저항 감소 → **관통 적용 순서 유지** | `mitigation()` 은 그대로다 (고정 감소 → 비율 감소 → 비율 관통 → 고정 관통) |

쌓는 방법(`on`)은 세 가지다: `auto` 공격 속도 × 평타 가동률 · `skill` 시전 빈도 × 공통 가정(30%) · `both` 둘의 합.
**스킬 쪽에 공통 가정 30% 를 쓰는 것은 새 가정이 아니다** — '실제로 쓰여 맞는 스킬 빈도' 를 세는 기존 기준과 같다.

# 9. C9-A4·A5 적용 (2026-11-26) — 칠흑의 양날 도끼 · 악의 · 부식

## 9.1 칠흑의 양날 도끼 (깎아내기) — 물리 피해 횟수로 센다

| 확인 | 어떻게 |
|---|---|
| **실제 물리 피해 발생 횟수**로 중첩 | 쌓는 속도 = 기본 공격(공격 속도 × 평타 가동률) + **물리 피해가 있는 스킬**의 시전 빈도 × 공통 가정 30% |
| 마법·고정 피해는 **안 센다** | 스킬의 피해 종류를 보고 거른다. 적응형은 그 챔피언의 주 능력치 쪽으로 (증강 효과 계산과 같은 규칙) |
| 평타·스킬 **중복 발동 방지** | 한 스킬은 피해 효과가 몇 개든 **한 번**만 센다. 기본 공격에 딸린 적중 효과도 따로 세지 않는다 |
| 최대 중첩·지속시간 | 5중첩 · 6초 (설명 그대로) → 공통 식이 포화 중첩과 쌓는 시간을 함께 본다 |
| 중첩 형성 시간·평균 감소량 | 가렌 3.14중첩 = **18.8%** · 애쉬 2.96중첩 = 17.7% · 173명 중앙값 **17.7%** (가장 낮음 13.2% · 가장 높음 23.8%) |

이동 속도(열정)의 **가동률 75% 가정은 그대로 두었다** — 깎아내기와는 다른 패시브다 (2절 지적).

## 9.2 악의 (증오안개) — 궁극기 피해 기준, 두 가동률

| 확인 | 어떻게 |
|---|---|
| 일반 스킬 빈도가 아니라 **궁극기 피해** 기준 | `on: "ult"` — 궁이 막히거나(증강) 궁에 피해 효과가 없으면 **0** |
| **한타 피해와 장기 초당 피해의 가동률 구분** | 한타: 3초 ÷ 한타 6초 = **0.5** · 길게: 3초 ÷ 그 챔피언의 궁 재사용 대기시간 (럭스 0.058 · 애니 0.034) |
| 장판 지속시간·궁 대기시간 반영 | 위 두 식이 각각 쓴다. 궁 대기시간에는 아이템의 궁 가속(경멸 20)이 이미 들어 있다 |
| **두 가동률 모두 추정값** | '한타 한 번 = 6초', '궁을 대기시간마다 한 번 쓴다', '궁을 쓰면 챔피언에게 맞는다' 는 모델 가정이다. 실제 판에서 재지 않았다 |
| **같은 가동률 중복 적용 방지** | 감소량은 10 × 가동률을 **한 번만** 곱한다. 초당 피해 쪽은 '저항 배수의 비'(`shredAdj`)로 한 번 보정하고, 장판 피해(`effects`)는 건드리지 않았다 |
| 고정 감소 **적용 순서** | `mitigation()` 그대로: 고정 감소 → 비율 감소 → 비율 관통 → 고정 관통 |

# 11. C9-B 설계안 (2026-11-26) — **구현 결과는 12절에 있다**

> 이 절은 승인 전에 쓴 설계안이다. 실제로 들어간 내용과 다른 곳이 한 군데 있다 (11.2 겹침 식 → 12.2).

## 11.1 무엇을 세려는 것인가

저항 감소는 **그 대상을 때리는 모두**에게 득이 된다. 지금은 내 피해에만 반영한다.
C9-B 는 **아군이 더 넣게 되는 피해**를 지원 지표에 더한다.

```
아군 한 명의 몫 = (그 아군이 깎인 상대를 때릴 때의 피해) − (깎이지 않은 상대를 때릴 때의 피해)
                = 그 아군의 초당 피해 × [ 물리 비중 × (물리 배율비 − 1) + 마법 비중 × (마법 배율비 − 1) ] × 한타 시간
  물리 배율비 = mitigation(상대 방어력, 그 아군의 ARPEN·LETHALITY, 내 감소) ÷ mitigation(상대 방어력, 그 아군의 관통, 감소 없음)
  마법 배율비 = 같은 식을 마법 저항력으로
```

- **고정 피해에는 저항 감소가 걸리지 않는다** → 비중에서 빠진다 (위 식에 고정 항이 없다).
- **아군 자신의 관통**으로 계산한다 (내 관통이 아니다). 관통과 감소는 적용 단계가 달라 둘 다 들어간다.
- 아군의 피해 유형 비중·초당 피해는 **F11 의 `calc`** 를 그대로 쓴다 (없으면 아래 대체 경로).
- **한타와 길게 싸울 때를 가른다**: 콤보 쪽은 `out.shred`, 초당 쪽은 `out.shredLong` (C9-A4 에서 이미 둘을 만들어 뒀다).
  **중첩 평균에 이미 들어 있는 가동률을 다시 곱하지 않는다** (7.1).

## 11.2 겹침 — 아군이 이미 같은 효과를 들고 있으면

비율 감소는 곱해서 쌓인다. 그러니 내 기여는 **'같이 걸었을 때 − 아군 혼자 걸었을 때'** 다.

```
내 기여(%p) = [1 − (1 − 내 감소)(1 − 아군 감소)] − 아군 감소 = 내 감소 × (1 − 아군 감소)
```

> **2026-11-26 정정 (구현에서는 이 식을 쓰지 않았다).** 위 식은 '같은 아이템을 둘이 들면 두 효과가 서로 곱해진다' 를 전제한다.
> 그런데 **같은 효과를 여럿이 들었을 때 게임이 어떻게 쌓는지 확인하지 못했다** (하나의 디버프를 같이 쌓을 수도 있다).
> 그래서 구현은 **같은 효과면 큰 쪽만** 세고 **서로 다른 효과만** 곱한다 (12.2) — 내 기여를 과대평가하지 않는 쪽이다. 미검증 항목 **F21**.

실제로 재 보면 (가렌 칠흑 18.8% + 진도 칠흑 13.2%): 같이 29.5% · 내 기여 16.3%p → **아군이 이미 들고 있으면 내 몫이 13.2% 줄어든다**.
고정 감소(악의)는 더해서 쌓이므로 겹쳐도 내 기여가 줄지 않는다 (상대 저항이 0 에서 잘리기 전까지).
아군의 감소는 **F11 에서 본 아군 아이템**으로만 센다 (보이지 않는 증강은 모른다 → 없는 것으로 두고, 그래서 내 기여를 **높게** 잡는 쪽이다).

## 11.3 기존 allyGain 과 어떻게 잇나

`allyGain(kind, amt, sec, hits, cap)` 은 **아군 강화**(공격 속도·공격력·적중 시·가속·피해량)를 '기준 아군(ALLY) 이 더 넣는 피해' 로 바꾼다.
단위·시간·대상 규칙을 확인했다.

| 것 | 지금 규칙 | C9-B 에서 |
|---|---|---|
| 단위 | 아군이 더 넣는 피해 1 = 지원 1 (체력 단위) | **같게 쓴다** (새 단위를 만들지 않는다) |
| 시간 | `min(효과 지속, AUTO_FIGHT_SEC=6초)` | 저항 감소는 한타 내내라 **6초** |
| 대상 수 | `ALLY_TARGETS = 1` (회복·보호막과 같은 기준) | **여기가 갈린다 — 11.4** |
| 아군 모델 | `ALLY` 상수 (원딜 29명 중앙값: 초당 977 · 물리 98.7%) | F11 이 있으면 **실제 아군**, 없으면 ALLY |
| 아군 가동률 | `EXP.allyUptime` (기본 1) | 같은 값을 쓴다 (새 가정 없음) |

→ `allyGain` 에 `kind: "allyShred"` 를 더하는 대신, **`metrics` 안에서 `out.shred` 가 정해진 뒤 한 번만** 계산해 `out.allyDmg` 에 더하는 쪽이 맞다.
저항 감소는 '효과 하나당 한 번' 이 아니라 '합쳐진 감소량 한 번' 이기 때문이다 (칠흑 + 부식을 따로 세면 겹침을 두 번 센다).

## 11.4 크기 — 그대로 더하면 개인 지표를 압도한다 (`node tools/c9b_scale.js`)

| 내가 든 것 | 내 한타 피해 | 아군 4명이 더 넣는 피해 (물리 팀 / 마법 팀 / 혼합 팀) |
|---|---|---|
| 가렌 + 칠흑 (방어력 18.8%) | 900 | **440 (48.9%)** / 107 (11.9%) / 268 (29.8%) |
| 룩스 + 악의 (고정 마저 5) | 812 | 55 (6.8%) / 99 (12.2%) / 56 (6.9%) |
| 룩스 + 부식 (방어력·마저 4.4%) | 629 | 126 (20.0%) / 80 (12.7%) / 90 (14.3%) |

- 위 표의 아군은 **아이템 2~3칸**짜리라 작게 나온 쪽이다.
- **지금의 기준 아군(ALLY, 18레벨 완성 빌드 초당 977)으로 세면 한 명이 +636**, 넷이면 **+2543 = 내 한타 피해의 2.8배**다.
  즉 **ALLY 상수 × 4 는 쓰면 안 된다.** 이번 조사의 가장 중요한 결론이다.
- 그래서 제안은 ⑴ **F11 의 실제 아군**을 쓰고 ⑵ 아군 수는 **지금의 `ALLY_TARGETS = 1` 규칙을 그대로** 두며
  ⑶ 아군 정보가 없으면 ALLY 한 명으로 세는 것이다 (지금 회복·보호막과 같은 보수적 기준).
  **가중치·목적 함수는 건드리지 않는다** — 크기를 맞추려고 가중치를 조절하지 않는다.
- 아군 피해 유형 비중은 **F5 수정 뒤 다시 쟀다**: 원딜 29명 중앙값 물리 **98.7%** · 마법 1.3%,
  메이지 35명 중앙값 물리 12.5% · 마법 87.5%, 전 챔피언 평균 물리 58.1% · 마법 40.7% · 고정 1.2%.
  **원딜 29명의 고정 비중을 모든 조합에 일괄로 쓰지 않는다** — 그러면 마법 저항력 감소(핏빛 저주·악의)가 거의 0 으로 깎인다.

## 11.5 내 몫과 아군 몫을 가른다

| 칸 | 무엇 |
|---|---|
| `out.combo` · `out.dps` | 내 피해 (지금 그대로) |
| `out.allyDmg` | 아군이 더 넣는 피해 — **저항 감소 몫을 여기 더한다** (아군 강화와 같은 칸) |
| `out.shredAlly` (새로) | 그중 저항 감소에서 온 몫만 따로 (근거 표시·점검용) |

## 11.6 캐시·성능

- 아군이 계산에 들어가면 **memo 열쇠에 아군 상태**(챔피언·레벨·아이템·증강 요약)가 들어가야 한다.
  지금 열쇠에는 기준 상대만 있다 → 아군이 바뀌었는데 옛 추천이 나오는 일을 막으려면 한 칸 늘려야 한다.
- 같은 아군 상태면 캐시를 그대로 쓴다.
- **아이템 후보마다 아군 4명의 빌드를 다시 계산하지 않는다**: 아군의 '기본 피해와 피해 유형 비중' 은 아군이 바뀔 때 한 번만 재고
  (F11 이 이미 그렇게 한다, 1.1ms), 후보마다는 **감소량만 바뀌므로 배율비 곱셈 한 번**이면 된다.
  즉 `아군 몫 = Σ 아군별 (초당 피해 × 비중 × 배율비 차)` 에서 앞 두 항은 캐시, 뒤 한 항만 다시 센다.

# 12. C9-B 구현 결과 (2026-11-26, 적용됨)

11절은 설계안이었다. 승인 때 받은 보완 사항을 반영해 구현했고, 아래가 **실제로 들어간 내용**이다.
11.2 의 겹침 식은 쓰지 않았다 (12.2 에서 바꾼 이유를 적는다).

## 12.1 계산식 — 무엇을 어떻게 세나

```
아군 한 명의 몫 = 그 아군의 초당 피해
                 × [ 물리 비중 × (물리 배율비 − 1) + 마법 비중 × (마법 배율비 − 1) ]
                 × 한타 6초(AUTO_FIGHT_SEC)

물리 배율비 = mitigation(상대 방어력, 그 아군의 비율 관통·고정 관통, 나+아군 감소)
            ÷ mitigation(상대 방어력, 그 아군의 비율 관통·고정 관통, 아군 감소만)
마법 배율비 = 같은 식을 마법 저항력으로
```

| 지적 | 어떻게 지켰나 |
|---|---|
| 실제 아군 각각의 피해 유형·피해량으로 | 아군 한 명씩 따로 센다 (`out.shredAlly.per`). F11 이 아군마다 잰 초당 피해·물리/마법 비중을 그대로 쓴다 |
| `ALLY_TARGETS = 1` 유지 → **평균**을 점수에 | 점수에 들어가는 값은 `avg = 합 ÷ 본 아군 수`. 회복·보호막과 같은 '아군 한 명' 기준이다 |
| 합계와 1인분을 갈라 기록 | `out.shredAlly.sum`(팀 합계) 과 `.avg`(점수에 들어가는 몫) 를 둘 다 남긴다. **점수에 더해지는 것은 `avg` 뿐이다** |
| 일부만 봤으면 본 아군만 | 본 아군으로만 평균을 낸다. 모자란 인원을 기준 아군(ALLY)으로 **채우지 않는다** |
| 전혀 못 봤을 때만 대체 모델 | `setAllies(null)` 이면 대체 모델 **한 명**: 초당 피해 977(= ALLY 평타 891 + 스킬 86) · 물리 98.7% · 마법 1.3% · **관통 0 · 저항 감소 0** |
| 고정 피해 제외 | 식에 고정 항이 없다. 고정 피해만 넣는 아군에게는 기여가 **정확히 0** (테스트로 고정) |
| 아군 자신의 관통 | 배율비의 분모·분자에 **그 아군의** 관통이 들어간다. 내 관통은 아군 쪽에 쓰이지 않는다 (테스트로 고정) |
| 아군 자신의 감소를 두 번 세지 않기 | 분모가 '그 아군이 **원래** 받던 피해 배율'(= 아군 자신의 감소만 적용)이라, 그 아군의 효과는 분자·분모에서 상쇄된다 |
| 내 피해와 아군 피해를 가르기 | 아군 몫은 `out.combo`·`out.dps` 에 들어가지 않고 **지원 쪽 `out.allyDmg`** 로만 간다 (아군 강화와 같은 칸) |
| 비율·고정 적용 순서 | 기존 `mitigation()` 을 그대로 쓴다: 고정 감소 → 비율 감소 → 비율 관통 → 고정 관통 |
| 비중을 잰 상대 = 배율비를 내는 상대 | 기준 상대가 바뀌면(적이 방어 아이템을 삼) **아군 피해 유형 비중도 다시 잰다** (`applyEnemyTarget` 이 값을 바꿨으면 아군을 다시 센다) |
| 한타와 장기를 섞지 않기 | 한타 쪽은 `out.shred`, 길게 싸울 때 쪽은 `out.shredLong` 으로 **따로** 센다. `out.allyDmg` 는 '한타 한 번' 단위라 **한타 쪽만** 더한다 (장기 쪽은 `out.shredAlly.long` 에 기록만) |
| 이미 들어간 가동률을 다시 곱하지 않기 | 평균 중첩(`shredExpect`)에 이미 쌓는 시간·지속시간이 들어 있다. 아군 쪽에서 가동률을 다시 곱하지 않는다 |

**역방향은 이번 범위 밖이다.** 아군의 저항 감소가 **내** 피해를 키워 주는 몫은 세지 않는다 (지금도 내 감소만 본다).
테스트로 고정해 두었다 — 아군을 바꿔도 내 `combo`·`dps` 는 그대로다.

## 12.2 같은 효과를 여럿이 들었을 때 (지적 2)

**확인하지 못했다.** 같은 아이템을 둘이 들면 하나의 디버프를 같이 쌓는지(최대 중첩 공유), 사람마다 따로 걸리는지 원본 설명에 없다.
그래서 **중복 기여를 과대평가하지 않는 쪽**으로 정했다.

| 경우 | 어떻게 세나 |
|---|---|
| **같은 효과** (같은 아이템·증강 — 능력치·중첩당 값·최대 중첩·지속시간·발동 조건이 모두 같다) | **큰 쪽만** 센다. 같은 값이면 내 기여는 **0** |
| **다른 효과** | 비율은 곱, 고정은 합 (C9-A2 와 같은 규칙). 겹치지 않는다 |

같은 효과인지는 **효과 서명**(`stat|발동조건|중첩당|최대중첩|지속시간|고정중첩평균`)으로 가른다.

실제로 잰 값 (가렌 칠흑 18.8% · 진도 칠흑 13.2%):

| | 아군이 칠흑을 안 들었을 때 | 아군도 칠흑 | 아군이 **다른** 효과(악의) |
|---|---|---|---|
| 아군이 받는 피해 배율 증가 | +11.0% | **+3.3%** | +11.0% |
| 내 기여 | 116 | **31** | 79 (아군 초당 피해가 달라진 몫) |

11.2 의 곱연산 식이었다면 내 기여가 16.3%p 였을 자리가, 이 규칙에서는 5.6%p 다. **F21** 로 등록했다.

## 12.3 기존 `allyGain` 과의 연결

`allyGain` 에 새 종류를 더하지 **않았다**. 저항 감소는 '효과 하나당 한 번' 이 아니라 **합쳐진 감소량 한 번**이라,
칠흑과 부식을 따로 세면 겹침을 두 번 센다. 그래서 `metrics` 안에서 `out.shred` 가 정해진 **뒤 한 번만** 계산해 `out.allyDmg` 에 더한다.

단위·시간은 기존과 같다: 아군이 더 넣는 피해 1 = 지원 1(체력 단위) · 한타 `AUTO_FIGHT_SEC` 6초 · 아군 한 명.

**초당 피해 × 6초 와 한타 피해는 같은 값이 아니다** (지적 4 확인 결과). 진 2194 vs 1355 (초당×6 이 62% 큼), 룩스 604 vs 934 (35% 작음).
`allyGain` 이 예전부터 `ALLY.autoDps × 초` 로 세 왔으므로 **같은 규칙(초당 × 6초)** 으로 맞췄다 — 한타 피해 모델과는 다른 값이라는 것을 여기 적어 둔다.

## 12.4 캐시·추천 갱신 (지적 5)

- **아군 지문**(`Stats.allyKey()`): 아군마다 챔피언·초당 피해·물리/마법 비중·관통 4종·들고 있는 저항 감소 서명. 아군이 바뀌면 지문이 바뀐다.
- 지문을 **계산 기억(memoKey)** 과 **화면 캐시 열쇠 4곳**(증강 목록·등급·빌드·게임 화면), **게임 연동 열쇠**(`applyLive`)에 넣었다.
- 아군 값을 다시 재는 것은 **아군이 바뀔 때와 기준 상대가 바뀔 때뿐**이다 (1.1ms). 아이템 후보마다 아군 빌드를 다시 계산하지 않는다 —
  후보마다 다시 하는 것은 **배율비 곱셈 한 번**(아군 한 명당 `mitigation` 4번)이다.

| 상황 | 결과 |
|---|---|
| 아군만 아이템을 삼 / 레벨만 오름 / 보이는 증강이 바뀜 | 지문이 바뀐다 → 아이템 순위·증강 추천·다음 구매·빌드를 다시 계산 (테스트로 고정) |
| 상대 저항이 바뀜 | 아군 피해 유형 비중을 다시 재고, 기준 상대 열쇠로 다시 계산 |
| 아군 정보가 없어짐 / 다시 보임 | `setAllies(null)` ↔ 실제 아군. 지문이 달라 다시 계산 |

## 12.6 아직 확인하지 못한 것

- **실제 게임 확인 0건.** 실제 판에서 아군 정보가 들어오는지·아군 몫이 추천에 어떻게 보이는지는 Phase 6 통합 검증에서 본다.
- 아군 증강은 **소환사 주문 칸에 보이는 것만** 확인된다. 안 보이는 증강의 저항 감소는 '없음' 으로 치므로 내 기여를 **높게** 잡는 쪽이다.
- 아군의 초당 피해·피해 유형 비중은 전부 **추정값**이다 (그 아군이 실제로 얼마나 때리는지는 모른다).
- 같은 효과를 여럿이 들었을 때의 실제 중첩 규칙 — **F21**.
- 아군을 한 명도 못 봤을 때 쓰는 대체 모델은 **18레벨 완성 빌드 원딜**이라 실제 아군(아이템 2~3칸)보다 크다 (636 vs 67~118).
  게임 안에서는 F11 이 아군을 읽어 주므로 대체 모델이 쓰이는 것은 **아군을 한 명도 못 읽었을 때와 화면에서 그냥 볼 때**다.
