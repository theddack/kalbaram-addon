# v0.1.94 Phase 4 — 6칸이 찬 상태 점검과 실제 화면 흐름 확인

수정은 하지 않았다. 확인한 것과 최소 수정안만 적는다.

---

## 1. 잘못 인식된 증강으로 6칸이 다 찬 상태에서 새 선택 화면이 오면

클릭으로만 잡은(짐작) 증강 6개로 칸을 채운 뒤 새 선택 화면을 넣어 봤다. jsdom 테스트와
실제 화면(브라우저) 둘 다 같은 결과였다.

| 확인한 것 | 결과 |
| --- | --- |
| 애드온 선택지 입력 칸 | **비어 있고 잠김** (`["", "", ""]`, 모두 disabled) |
| 게임 화면 카드 | **0장** |
| 선택지 추천 영역 | "증강 4개를 다 골랐어요." (6칸인데 4개라고 함) |
| 증강 목록 | "증강을 다 골랐어요" 요약 |
| 새로 누른 증강(클릭) | **안 들어감** |
| 증강 칸이 새로 확인해 준 증강(`hudPicked` 추가) | **안 들어감** |
| 증강 칸이 "이게 아니라 저거"라고 짝지어 알려 줌(`replaces`) | **들어감** — 바로잡힘 |
| 능력치 대조(`statCheck`)로 바로잡기 | 칸 수와 무관하게 동작 |
| 칸을 눌러 직접 빼기 | 됨 (Phase 3에서 고침) |

### 무엇이 문제인가

`applyAug()` 에 `AUG_MAX` 를 보는 자리가 세 군데 있는데, 셋 다 **칸이 찼으면 새 정보를 버린다.**

```js
if (add.length && state.chosen.length < AUG_MAX) { ... }        // 증강 칸이 새로 확인해 준 증강
if (A.offers && state.chosen.length < AUG_MAX) { ... }          // 새 선택 화면
if (state.chosen.length < AUG_MAX && !이미있음) chosen.push(a);  // 새로 누른 증강
```

모양이 2026-10-15 케일 사례와 같다. 그때는 상한이 4라 4칸에서 선택지를 버렸고, 지금은 6칸에서 버린다.
칸이 **맞게** 찼다면 맞는 동작이다(게임에서 7개를 고를 수 없다). 칸이 **틀리게** 찼을 때만 문제가 된다.

### 수동 삭제 없이 복구되나

**부분적으로만 된다.** 증강 칸이 짝을 지어 알려 주는 경우(`replaces`)와 능력치 대조는 칸 수와 상관없이
바로잡는다. 그 밖에는 — 증강 칸이 새 증강을 그냥 보여 주거나, 사용자가 새 증강을 고르는 경우 —
사람이 칸을 눌러 빼기 전까지 안 들어간다.

### 이 상황이 실제로 있었나

기록 7판에는 **없다.** 가장 많이 고른 미스 포츈이 6개였고 그 6개는 맞았다. 즉 지금 보고 있는 것은
"있을 수 있는" 상태지 "일어난" 상태가 아니다. 그래서 수정 범위를 좁게 잡는 쪽을 권한다.

## 2. 최소 수정안 (적용 안 함)

### N1 — 칸이 찼어도 선택 화면은 보여 준다 (권장)

`if (A.offers && state.chosen.length < AUG_MAX)` 의 칸 수 조건을 없앤다.
선택 화면이 떴다는 것은 게임이 아직 더 고르게 한다는 뜻이므로, 칸이 찼다면 칸 쪽이 틀린 것이다.
선택지와 평가가 보이고 게임 화면 카드도 뜬다. 고르기는 여전히 상한에서 막히지만,
사용자가 틀린 칸을 눌러 뺀 뒤 바로 고를 수 있다.

바뀌는 것: 화면에 선택지가 보임. 추천 계산식·OCR 임계값은 안 건드림.

### N2 — 칸이 찼는데 새 선택이 들어오면 확인 안 된 짐작 하나를 밀어낸다 (선택)

```js
// 7개를 고를 수는 없다 → 앞의 짐작 중 하나가 틀렸다는 뜻. 확인된 것만 차 있으면 받지 않는다
function makeRoom() {
  if (state.chosen.length < AUG_MAX) return true;
  const i = state.chosen.findIndex((a) => !(state.hudSure && state.hudSure.has(a.id)));
  if (i < 0) return false;
  state.chosen.splice(i, 1);
  return true;
}
```

이걸 넣으면 수동 삭제 없이 복구된다. 다만 **지우는 동작을 다시 들이는 것**이라 조심해야 한다.
Phase 3에서 지운 코드와 다른 점은 근거다. 그쪽은 '선택 화면이 떴다'는 간접 신호로 지웠고,
이쪽은 '상한을 넘는 새 선택이 실제로 들어왔다'는 직접 신호로 지운다. 그래도 밀려나는 짐작이
사실 맞았을 가능성은 남는다(v0.1.15에 비슷한 사고가 있었다).

기록에 이 상황이 없으므로, **N1만 넣고 N2는 안 넣는 쪽**을 권한다.

### N3 — 문구를 실제 개수에 맞춘다 (곁다리)

6칸인데 "증강 4개를 다 골랐어요"라고 한다. `renderOfferResult()` 와 `renderAugs()` 의 문구만
고른 개수를 쓰게 한다. 동작은 안 바뀐다.

## 3. 실제 화면 흐름 점검 (지금 환경에서 할 수 있는 것)

`web/` 를 로컬에 띄우고 브라우저에서 실제 화면을 조작했다. 테스트 코드가 아니라 실제 `index.html` 이다.

| 흐름 | 결과 |
| --- | --- |
| 챔피언 검색 → 미스 포츈 선택 | 정상 |
| 증강 3개 클릭으로 잡기 | 칸에 표시, '클릭으로 앎' 꼬리표 |
| 4번째 클릭 | 들어감 |
| 그 뒤 새 선택 화면 | **4번째가 남음** (Phase 3 수정이 실제 화면에 반영됨) |
| 그때 선택지 입력 칸 | 3개 다 채워지고 잠기지 않음 |
| 그때 선택지 평가 | '강한 선택'·'재미있는 선택'·살 아이템까지 정상 계산 |
| 5·6번째 클릭 | 들어가고 **칸 6개가 다 보임** (Phase 3 수정 반영) |
| 6칸에서 새 선택 화면 | 위 1번의 문제 그대로 |
| 칸을 눌러 빼기 | 됨 |

### 실제 게임이 있어야 확인되는 것 (여기서 못 함)

- 게임 증강 칸이 실제로 몇 개까지 보여 주는지
- 증강 칸 그림 읽기(OCR)의 실제 정확도 — 지금은 기록된 이벤트를 넣어 흉내만 냈다
- 새로고침 직후 클릭에서 이름을 못 읽는 그레이브즈 유형
- 게임 화면 위에 그리는 카드의 실제 위치·가림 여부
- 헤드라이너(K/DA)로 5·6번째 증강을 실제로 받는 흐름
- 6칸이 **틀리게** 찬 상태 자체 — 기록 7판에 없다
