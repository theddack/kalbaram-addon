# 1. 기존 검증 도구 전수 조사

## 1.1 `global.Stats` 교체가 문제가 되는 조건

문제는 "`global.Stats` 를 쓴다" 가 아니라 **한 프로세스에서 엔진을 두 개 불러 놓고 점수·추천까지 견주는 것**이다.
`web/scoring.js` 3번째 줄이

```js
const Stats = typeof module !== "undefined" ? require("./stats.js") : root.Stats;
```

라서, node 에서는 **파일에서 읽은 엔진이 고정**된다. 뒤늦게 `global.Stats` 를 바꿔도 점수 쪽은 안 바뀐다.
`web/` 안에서 이 꼴은 `scoring.js` 한 군데뿐이다 (`grep` 확인).

## 1.2 도구 33개 조사 결과

`global.Stats` 에 대입하는 도구·테스트는 39곳이지만, 그중 **엔진을 두 개 부르는 것은 둘뿐**이다
(나머지는 '지금 엔진 한 개를 브라우저처럼 전역에 꽂는' 한 줄짜리 준비 코드다).

| 도구 | 엔진을 두 개 부르나 | 무엇을 견주나 | 판정 |
|---|---|---|---|
| `tools/e1e2_check.js` | 예 (`OLD_STATS`) | §1 지표 + **아이템 Top3** | **§1 Top3 는 무효** — 지표(`St.evaluate` 직접 호출)는 맞다 |
| `tools/c1c2_check.js` | §4 만 (`OLD_STATS`) | §1~3 은 **입력값**(상대 회복량·추가 체력)을 바꿔 견준다 · §4 는 `OldStats.evaluate` 직접 호출 | **문제 없음** — 엔진을 바꿔치기해 점수를 견주는 자리가 없다 |
| 나머지 31개 | 아니오 | 지금 엔진 한 개 | 해당 없음 |

C1·C2 는 "엔진이 아니라 **기준 상대에 넣는 값**을 고친 수정" 이라, 같은 엔진에 값을 달리 넣어 견주는 게 맞는 방법이다.
그래서 **C1·C2·C9-A1·A2·A2.5 의 검증 결과는 다시 재지 않아도 된다**
(C9 쪽은 애초에 파일 교체 방식 `tools/c9_shred_check.js` 로 쟀다).

**재검증이 필요했던 것은 E1·E2 하나뿐이고, 이미 파일 교체 방식으로 다시 쟀다** (`수정결과` §15).

`tests/data/rec_baseline.json` 은 **그대로 두었다** (F1 로 등록된 Top1 3 · Top3 10 · Top6 8 · 증강 등급 4장면 차이도 그대로).

## 1.6 조사 중 찾은 함정 (민감도 조사용)

`stats.js` 는 능력치 객체마다 `Object.entries` 결과를 `WeakMap`(`ENTRIES`)에 기억해 둔다.
그래서 **`item.passiveStats.X = 값` 처럼 속성만 바꾸면 계산에 안 먹는다** (앞 한 번 읽은 목록을 계속 쓴다).
객체를 통째로 새로 꽂아야(`item.passiveStats = { ...., X: 값 }`) 다시 읽는다.
또 아이템 규칙값은 `build_data.py` 가 `data.json` 의 `item.passiveStats` 로 **구워 넣기** 때문에,
`rules.json` 이나 `d.rules.items` 를 런타임에 바꿔도 아이템 쪽은 안 바뀐다 (증강 쪽은 `d.rules` 를 그 자리에서 읽는다).
`tools/f8_probe.js` 에 주석으로 남겼다. 처음 민감도 측정에서 "변화 0명" 이 나왔던 원인이 이것이다.

# 2. F8 · E4 — 원형질 안전벨트

## 2.1 두 문제를 가른다

| 구분 | 무엇 | 확인 |
|---|---|---|
| (가) **분류 오류** | 회복이 아닌 **최대 체력 +300** 이 '자기 회복' 칸에 들어 있다 | 원본 문구로 확인 (아래) |
| (나) **회복량 부족** | 실제 회복에는 **추가 방어력·마법 저항력의 175%** 가 붙는데 규칙은 그 몫을 통째로 뺐다 | 원본 문구로 확인 |

두 오류는 **방향이 반대**다. 대부분의 챔피언에서는 (가) 때문에 과대평가, 탱커에서는 (나) 때문에 과소평가다.

## 2.2 원본 수치는 '없는' 게 아니었다 (E4 전제 정정)

지금까지 E4 를 "원본 수치 없음 → 보류" 로 두었는데, `data.json` 의 `desc` 가 값이 안 풀린 쪽이라 그렇게 보였다
(`최대 체력을 0 얻고 … 체력을 0 회복`). **같은 아이템의 `passiveHtml` 에는 값이 풀려 있다**:

> 생명선 (60초) 체력이 30% 아래로 떨어질 만큼 피해를 받으면 5초 동안 최대 체력을 **100~300(레벨 비례)** 얻고
> 지속시간 동안 체력을 **100~400(레벨 비례) + 175% 추가 방어력 + 175% 추가 마법 저항력** 회복합니다.

→ 18레벨 기준: **최대 체력 +300 (5초 동안만)** + **회복 400 + 1.75 × (추가 방어력 + 추가 마법 저항력)**.
재사용 대기시간은 `desc` 의 `(0초)` 가 아니라 **60초**다 (지금 규칙의 '한타 1번에 1번' 가정과 맞는다).

## 2.3 `cv.selfHeal` 계열을 쓰는 전부 (3개)

| 종류 | 이름 | 열쇠·값 | 규칙이 적은 근거 | 원본 효과 | 판정 |
|---|---|---|---|---|---|
| 아이템 | 원형질 안전벨트 | `selfHeal: 700` | "체력 +300 + 회복 400 = 700 (저항 비례분은 뺌)" | 위 2.2 | **분류 오류 + 회복량 부족** |
| 증강 | 감시의 장막 (`VeilOfWarding`) | `selfHeal: 396` | "적 스킬 한 번을 막음 → 막은 피해만큼 버티는 힘" | "30초마다 적의 다음 스킬을 막아 주는 **주문 방어막**" | **분류 오류** — 회복이 아니라 **피해 흡수**다 |

`396` 은 '전 챔피언 18레벨 추천 빌드의 스킬 한 방 피해 중앙값' 이라는 **모델 가정값**이다 (측정값 아님).

## 2.4 지금 어디로 전달되나 (람머스로 확인)

| 받는 쪽 | 전달되나 | 값 |
|---|---|---|
| 자기 생존력 `ehp` (`extraHp`) | **예** | 5571 → 8030 (`selfHealAll` 0 → 700) |
| 죽음의 순환 `healToDamage` | **예** | 회복 → 피해 **490** (방어 전) · 맞는 피해 300.6 |
| 상대 회복량 추정 `app.js selfHealOf` | **아니오** | `itemSelfHeal` 0 → 0 |

`selfHealOf()` 는 `m.selfHeal + m.vampHeal + m.itemSelfHeal` 만 읽는데, 규칙값 `cv.selfHeal` 은 그 세 칸 어디에도 안 들어간다.
→ **같은 700 을 죽음의 순환에는 '회복' 으로 주면서, 상대 회복량·치유 감소(고통스러운 상처)에는 안 센다.** 앞뒤가 맞지 않는다.

(참고: 체력 **재생**은 죽음의 순환의 발동 조건에 들어가지만 지금 모델에 아예 없다 → 후속 F10.)

## 2.6 수정안 → **승인받아 적용했다** (2026-11-25, `수정결과` §17·§18)

**원칙: 지금 쓰는 가정값(700·396)의 크기는 그대로 두고, '종류' 만 가른다.** 버티는 힘은 지금과 같아야 한다.

- **A. 칸을 가른다** — `selfHeal`(진짜 회복) / `selfHp`(최대 체력·현재 체력 증가) / `selfAbsorb`(보호막·피해 흡수) 세 열쇠.
  - `selfHealAll` = `selfHeal` 계열만 → 죽음의 순환은 이 값만 읽는다.
  - 버티는 힘 `extraHp` = 세 칸의 합 → **EHP 는 한 글자도 안 바뀐다**.
  - 선례: 맬모셔스의 아귀는 이미 `ehpMagFlat: 300` 으로 '보호막은 회복이 아니게' 넣어 두었다.
- **B. 값은 쪼개기만 한다 (새 수치 금지)**
  - 원형질 안전벨트: `{ selfHeal: 400, selfHp: 300 }` — 합 700 유지. 저항 비례분은 **이번엔 넣지 않는다** (B 안의 범위 밖, 아래 C).
  - 감시의 장막: `{ selfAbsorb: 396 }` — 값 그대로, 종류만 바꾼다.
- **C. 저항 비례 회복(2.1 (나))은 따로 승인받는다** — 챔피언마다 달라지므로 추천이 실제로 바뀐다. B 와 한 커밋에 섞지 않는다.
- **D. 상대 회복량 추정과의 앞뒤 맞추기** — `cv.selfHeal` 을 `itemSelfHeal` 에 넣을지(= 치유 감소 대상이 될지)는
  C1 과 닿아 있으므로 따로 본다. 지금은 '죽음의 순환에는 회복, 치유 감소에는 비회복' 이다.

**실제 결과** (A·B·C 를 두 커밋으로 나눠 적용한 뒤 잰 값, `수정결과` §17.2·§18.2):
분류 수정만으로 죽음의 순환 1순위 **14명**(민감도 예상 16명과 가까움) · 정령의 형상+죽음의 순환 **42명** ·
기준선 263장면과 실게임 169장면은 그대로. 이어서 원본 계수(C)까지 넣으니 **빌드 칸 15장면**(탱커 11명)이 바뀌었다.

# 3. F5 — 카서스의 '마법 비중 12.5%'

## 3.1 원인: 피해 유형 분리 도구가 아니라 원본 피해 모델

`tools/ally_damage_mix.js` 는 엔진의 `autoDps + skillDps` 를 저항 계수로 갈라낼 뿐이고,
갈라낸 합과 실제 피해의 차이는 **0.0%** 다 (1차 분해는 정확하다). 문제는 `skillDps` 쪽이다.

if (cdBase > 0.5) out.skillDps += dmg / Math.max(cd, 0.5);

# 4. C9 후속 구현안 보완

## 4.1 아군 피해 비중 — 고정하지 않는다

- **실제 아군 정보는 이미 들어온다.** `desktop.py parse_live()` 가 `allies` 를 만든다(나 포함, 팀 기준).
  다만 **웹(`web/app.js`)이 그 값을 아직 안 읽고**, 한 판 기록(`events.json` 의 `start`)에도 `enemies` 만 남는다.
- 그래서 C9-B 는 **두 갈래**로 간다.
  - **아군을 알 때**: 그 아군들의 18레벨 추천 빌드로 물리·마법 비중을 그 자리에서 구한다 (고정 숫자를 안 쓴다).
  - **모를 때만**: 기본 모델(`ALLY`)을 쓴다. 이때도 **원딜 한 종류로 고정하지 않는다** — C9-B0 가 보여 준 것처럼
    원딜 98.6/1.4 와 메이지 12.8/87.2 는 완전히 다르다.
- **임의의 비율을 확정하지 않는다.** 기본 모델의 비중을 어떤 값으로 둘지는 F5 편향을 잰 뒤에 따로 승인받는다.
- 기록에 `allies` 가 없으니 **기존 5판으로는 아군 인지 모델을 재생 검증할 수 없다**. 먼저 기록에 남기는 것부터다 (후속 F11).

## 4.2 평균 중첩과 가동률을 겹쳐 쓰지 않는다

`shredExpect()` 의 평균 중첩에는 **이미 지속시간이 들어 있다** (`s* = min(maxStacks, rate × dur)`).
여기에 가동률을 또 곱하면 지속시간을 두 번 세는 셈이다. 그래서 규칙을 못 박는다.

| 효과 | 쓰는 값 | 가동률 |
|---|---|---|
| 중첩형 저항 감소 (칠흑·부식) | `shredExpect()` 평균 중첩 | **곱하지 않는다** |
| 악의 — 한타 안 가동률 | 한타 피해 쪽 | `fightUptime` **만** |
| 악의 — 장기 가동률 | 초당 피해 쪽 | `ultUptime` **만** |

두 가동률은 **서로 독립**이고, 한 값에 둘을 같이 곱하지 않는다.
열쇠를 `fightUptime` / `ultUptime` 으로 갈라 두어 같이 쓰면 테스트가 실패하게 한다.
(앞 판 문서에 '두 가동률을 곱한다' 고 적었던 서술은 **폐기**다.)

## 4.3 음수 저항 — 지금 결과는 지금 데이터에서만이다

`tools/c9_shred_check.js` 의 측정: 관통 아이템 6칸을 다 껴도 가장 낮은 값이 **방어력 33.4 · 마법 저항력 14.5** →
`Math.max(0, …)` 클램프는 실제로 쓰이지 않는다.

**이 결론은 '2026-11-17 빌드 데이터(16.22.1) · 저항 감소가 핏빛 저주 하나뿐 · 아군 몫 미연결' 이라는 지금 범위에서만 성립한다.**
C9-A4(칠흑·악의 연결) · A5(부식) · B(아군 몫) 를 붙이면 감소와 관통이 겹치므로 **그때 다시 재고**,
클램프가 실제로 걸리는 장면이 생기면 그 시점에 보고한다. (`--positive` 처럼 측정 자체를 되풀이할 수 있게 도구에 남겨 두었다.)

## 5.2 C2 '한 판에 1.7초' → **5판 전체** 기준이다

재계산 횟수는 **5판 합계 57회 → 86회**, 늘어난 29회도 5판 합계다.
따라서 **1.7초는 5판 전체**이고, **판당 평균은 29/5 ≈ 5.8회 × 57ms ≈ 0.33초**다. 판마다의 분포는 재지 않았다.

## 5.4 전 챔피언 '57.7% + 34.2% + 0.0%' 가 100% 가 안 되는 이유

**세 비중을 각각 따로 중앙값 낸 값이기 때문이다.** 물리 중앙값을 만든 챔피언과 마법 중앙값을 만든 챔피언이 서로 다르다.
한 챔피언 안에서는 언제나 정확히 100% 다 (1차 분해 오차 0.0%). 합이 맞는 값은 평균이다.

| 묶음 | 중앙값 (합) | 평균 (합) |
|---|---|---|
| 기준 아군 = 원딜 29명 | 물리 98.6 · 마법 1.4 · 고정 0.0 (**100.0%**) | 물리 92.0 · 마법 8.0 · 고정 0.0 (**100.0%**) |
| 전 챔피언 173명 | 물리 57.7 · 마법 34.2 · 고정 0.0 (**92.0%**) | 물리 58.8 · 마법 40.0 · 고정 1.2 (**100.0%**) |

원딜 쪽은 우연히 100% 로 떨어졌을 뿐이다. `tools/ally_damage_mix.js` 가 이제 합과 평균을 함께 찍는다.
**앞 판에 적은 '마법 저항력 감소 아군 몫을 유형 구분 없이 더하면 약 70배 과대평가' 는 중앙값(1.4%) 기준이다.**
평균(8.0%) 으로 보면 약 12배다. 어느 쪽이든 유형을 갈라야 한다는 결론은 같지만, **70배는 중앙값 기준임을 밝혀 둔다.**
